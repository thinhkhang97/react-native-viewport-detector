# react-native-viewport-detector v2 — Design

Status: draft for review · Date: 2026-11-04 · Owner: Khang Nguyen (@thinhkhang97)

## 1. Intent

v1 tells a component whether it is inside the visible part of a scroll container. It works (1.0.8 fixed the
coordinate-space, Android-flattening and nested-provider bugs), but every detector runs its own `setInterval` and a
native `measureInWindow` round trip, so it burns CPU while nothing moves, lags by up to `frequency` ms, and exposes an
API nobody already knows.

v2 makes the library **the container-aware, event-driven in-view hook for React Native**:

- updates are driven by scroll/layout events, so an idle screen costs nothing and a scrolling one costs one batched
  pass per frame;
- visibility is computed against the nearest scroll container *and* every ancestor container (nested and horizontal
  lists work), which neither leading competitor does;
- the API mirrors the web's `react-intersection-observer` (`useInView`, `threshold`, `rootMargin`, `triggerOnce`), so
  developers — and coding agents — write correct code on the first try;
- it runs in Expo Go with no native code, and can transparently use faster engines when the app provides them.

### Why now

Research on 2026-11-04 (npm/GitHub data, competitor source reads, on-device probes) found:

| Library | Weekly dl | Mechanism | Main gap |
|---|---|---|---|
| react-native-intersection-observer (zhbhun) | 32k | onScroll + cached `measureLayout`, JS arithmetic | single root only (#13), slow >600 items (#7), breaks with native-driver scroll (#22), Fabric regressions (#15, #17), no hook |
| @futurejj/react-native-visibility-sensor | 18k | per-item `setInterval(100)` + `measure()` | window-only (no container clipping), re-renders visible items every 100 ms, Android always false (#37) |
| react-native-viewport-detector 1.0.8 | 2k | per-item `setInterval` + `measureInWindow` | idle CPU cost, unfamiliar API |
| FlatList / FlashList / Legend List viewability | core / 3.3M / 1.5M | list layout model | row-level only; cannot track an arbitrary child or a nested carousel |

Nobody combines event-driven updates + container clipping + nested scrollers + a hook API + impression semantics
(dwell time, pause on background). That is the slot v2 takes.

Engine probes (iOS 18.1 simulator, Expo Go, Expo SDK 58 / RN 0.88): `globalThis.IntersectionObserver` is **absent**
(RN's built-in IO is still behind the `enableIntersectionObserverByDefault` canary flag, default `false`);
`element.getBoundingClientRect()` is **present and synchronous**.

## 2. Goals, non-goals, anti-goals

**Goals (v2.0)**

1. Hook-first API compatible in shape with `react-intersection-observer` (web), plus an `<InView>` component.
2. Event-driven JS engine: zero timers and zero native calls while idle; at most one batched measurement pass per
   animation frame while anything relevant changes.
3. Correct for nested roots (vertical list containing horizontal carousels, any depth), horizontal lists, headers /
   safe-area insets, and roots that themselves move.
4. Multi-threshold support with real intersection ratios and `rootMargin`.
5. Impression features: `delay`/dwell time before reporting visible, automatic pause when the app is backgrounded,
   `skip` for screen-focus integration.
6. Works in Expo Go and bare RN, old and New Architecture, iOS and Android, with no required peer deps beyond
   `react` and `react-native`.
7. v1 code keeps working on v2 (deprecated, warns once in dev).
8. Ships compiled JS + `.d.ts`; includes a Jest mock so users can unit-test their components.
9. Documentation optimised for humans and coding agents (see §8).

**Non-goals (v2.0)** — designed for, built later:

- Reanimated / UI-thread engine (v2.2).
- Native IntersectionObserver engine wiring beyond auto-detection (v2.1).
- Custom native module (Expo Modules / Nitro) with occlusion detection (v3, only if demanded).
- Row-level list viewability: FlatList/FlashList already do it; v2 complements, not replaces, them.
- Web support via react-native-web (may work, not tested or promised).

**Anti-goals** — failure even if it "works":

- Any always-on timer or per-frame work while the screen is idle (sole exception: the deprecated v1 exports, §4.4).
- Re-rendering a component when its visibility did not cross a threshold.
- An API that requires wrapping each list in a library-specific HOC (zhbhun's `withIO` pain).
- Requiring a dev build / native code for the default path.
- Breaking a 1.0.8 user's build on upgrade.

## 3. Constraints

- Peer deps: `react >= 18`, `react-native >= 0.72` (**owner decision**: React 17 / RN 0.68–0.71 users stay on the
  `1.x` line). React 18 APIs (`useSyncExternalStore`, automatic batching, `useId`) may be used freely. Synchronous
  reads are used only when available (RN ≥ 0.82 DOM-like refs); older versions use the async fallback.
- "Don't break a 1.0.8 user" (anti-goal) means: on a supported React/RN version, v1 code compiles and behaves the same.
- Must pass the same device matrix as 1.0.8: Android emulator + iOS simulator via Expo Go (latest SDK), plus one bare
  RN app on the oldest supported RN version.
- Bundle: no runtime dependencies. Target < 6 kB min+gz for the core entry.
- `master` is protected: PRs only, CI (`Typecheck and test`) must pass.
- Maintainer preference: maintainability over micro-performance where they conflict.

## 4. Public API

Package name stays `react-native-viewport-detector`. Entry points:

| Import | Contents |
|---|---|
| `react-native-viewport-detector` | `ViewportProvider`, `useViewportRoot`, `useInView`, `InView`, types, v1 compat exports |
| `react-native-viewport-detector/jest` | Jest mock helpers |
| `react-native-viewport-detector/reanimated` | reserved for v2.2; not published in v2.0 |

### 4.1 Roots

A *root* is a scroll container (or any view) against which visibility is measured. Roots nest; a target is visible
only where it intersects **every** ancestor root and the window.

```tsx
// Option A — wrap any scrollable; the provider injects scroll/layout handlers into its single child.
<ViewportProvider rootMargin={{ bottom: 200 }}>
  <ScrollView>{/* ... */}</ScrollView>
</ViewportProvider>

// Option B — hook for lists that need explicit wiring (FlashList, Legend List, Animated.FlatList).
const root = useViewportRoot({ rootMargin: 100 });
<FlashList {...root.scrollProps} ref={root.ref} /* ... */ />
```

- `ViewportProvider` clones its single child, composing (never replacing) the child's own `onScroll`, `onLayout`,
  `onContentSizeChange`, `onMomentumScrollEnd`, `onScrollEndDrag`, and sets `scrollEventThrottle={16}` unless the child
  sets one. It measures the child as the root rectangle.
- `useViewportRoot()` returns `{ ref, scrollProps, Provider }` for cases where cloning cannot work; `Provider` must wrap
  the list's content consumers (documented with FlashList and Legend List examples).
- With no root in the tree, the window is the root, and the target is re-measured only on mount, its own
  `onLayout`, `Dimensions` and `AppState` changes. **A provider is required to track scrolling** — there is no
  global scroll signal in JS and the anti-goals forbid polling. In `__DEV__`, a target that finds no root warns once
  ("wrap your ScrollView in <ViewportProvider>"), suppressible with `root={null}` for intentionally static screens.
  Docs and every recipe lead with the provider. *(Author's call.)*
- When the scroll handler is an `Animated.event` with `useNativeDriver: true`, JS receives no scroll events; the
  provider detects this (handler is not a function) and falls back to frame-driven checks only while a touch/momentum
  is active, warning once in dev. (Proper support arrives with the Reanimated engine.)

### 4.2 `useInView`

```ts
function useInView(options?: InViewOptions): InViewResult;

interface InViewOptions {
  threshold?: number | number[];        // default 0; ratio of target area that must be visible
  rootMargin?: number | Partial<Record<'top' | 'right' | 'bottom' | 'left', number>>; // px, grows/shrinks the root
  triggerOnce?: boolean;                // stop observing after first time inView becomes true
  skip?: boolean;                       // pause observing (e.g. !isFocused); keeps last state
  initialInView?: boolean;              // value before the first measurement, default false
  delay?: number;                       // ms the target must stay past threshold before inView flips true
  onChange?: (inView: boolean, entry: ViewportEntry) => void;
}

interface InViewResult {
  ref: (node: View | null) => void;     // callback ref; attach to any host view
  inView: boolean;
  entry?: ViewportEntry;
}

interface ViewportEntry {
  isIntersecting: boolean;
  intersectionRatio: number;            // 0..1, area-based
  boundingClientRect: Rect;             // window coordinates
  intersectionRect: Rect;
  rootBounds: Rect | null;              // effective root after margins and ancestor clipping
  time: number;                         // performance.now() at measurement
}
```

Semantics match the web library: `inView` flips when the intersection ratio crosses any threshold in either direction;
`onChange` fires only on crossings; component re-renders only when `inView` or `entry` (if read) changes. Array return
form `const [ref, inView, entry] = useInView()` is also supported, as on the web.

`delay` implements dwell time: entering is reported only after the target has stayed past threshold for `delay` ms;
leaving is reported immediately.

App background: while `AppState` is not `active`, all targets report `inView=false` (with `onChange`) and observation
pauses; on return they are re-measured. Opt-out: `ViewportProvider pauseWhenInactive={false}`.

### 4.3 `<InView>`

```tsx
<InView threshold={0.5} triggerOnce onChange={(inView) => track(inView)} style={styles.card}>
  {({ inView }) => <Card highlighted={inView} />}
</InView>
```

Renders a host `View` (`collapsable={false}`) with the ref attached; accepts `InViewOptions` + `ViewProps`; children
may be nodes or a render function.

### 4.4 v1 compatibility

**Owner decision: v1 exports keep polling.** v1 users put `ViewPortDetectorProvider` (a plain `View`, accepting any
children) around a ScrollView and rely on per-detector polling to see scrolls, animations, data arriving and keyboard
changes. Removing polling would make their apps compile and then silently stop updating, so:

- `ViewPortDetectorProvider` and `ViewPortDetector` keep 1.0.8 behaviour exactly, including the `frequency` interval,
  `percentWidth`/`percentHeight` per-axis checks, `runOnce`, `enabled`, transition-only `onChange`, nested-provider
  clipping and `measureInWindow`. They are an **explicit, documented exception** to the zero-timer anti-goal, scoped
  to the v1 exports only.
- Implementation should reuse the shared geometry module (intersection, nested clipping) but keep the v1 polling
  scheduler separate from `JsEventEngine`; the 1.0.8 Jest suite is carried over unchanged as the compat test suite.
- A v1 detector placed inside a v2 `ViewportProvider` still polls (no mixing of engines); documented.
- Each v1 export logs one `console.warn` in `__DEV__` pointing to the migration guide. Removed in v3.
- A `1.x` branch receives critical fixes only, published with `npm publish --tag v1`.

## 5. Engine architecture

```
useInView / InView ──▶ Registry (per root tree) ──▶ Engine
                                                    ├─ JsEventEngine      (default, v2.0)
                                                    ├─ NativeIOEngine     (auto when global IO exists, v2.1)
                                                    └─ ReanimatedEngine   (opt-in subpath, v2.2)
```

Engine interface (internal, but stable enough for the later engines):

```ts
interface Engine {
  observe(target: Target, root: RootHandle | null, opts: NormalizedOptions, cb: (e: ViewportEntry) => void): () => void;
  invalidate(reason: InvalidateReason): void; // scroll | layout | content-size | app-state | dimensions | manual
}
```

Engine choice: `ViewportProvider engine?: 'auto' | 'js'` (default `'auto'`; in v2.0 `'auto'` resolves to `'js'`).

### 5.1 JsEventEngine (v2.0)

- **Registry:** one per provider tree; roots form a tree mirroring React nesting (a root registers with its nearest
  ancestor root via context). Targets register with their nearest root.
- **Invalidation sources:** root `onScroll` (16 ms throttle), `onLayout`, `onContentSizeChange`, momentum/drag end,
  `Dimensions` change, `AppState` change, target mount/`onLayout`, option changes, and an imperative
  `useViewportRoot().invalidate()` for cases the library cannot observe (parent transforms, keyboard).
- **Scheduling:** invalidations set a dirty flag and request one `requestAnimationFrame`; the frame callback runs one
  pass for the dirty subtree. No timers exist when nothing is dirty. After a scroll ends, one trailing pass runs to catch
  the final position.
- **Measurement:** for each dirty root (top-down) and its targets:
  - if the node exposes `getBoundingClientRect` (RN ≥ 0.82), read synchronously;
  - otherwise batch `measureInWindow` calls and resolve the pass when all callbacks return.
  - Effective root rect (author's call, mirrors web IO where the margin belongs to the root that declares it):
    - outermost root: `expand(rootRect ∩ window, root.rootMargin)` — the margin is applied **after** window
      clipping, so a `bottom: 200` preload margin reaches 200 px below the screen;
    - nested root: `expand(rootRect, root.rootMargin) ∩ parentEffective` — parent margins carry through, so a carousel
      item 150 px below the screen counts as in view under an outer `bottom: 200`, and a nested root's own margin
      cannot exceed what its ancestors allow;
    - target-level `useInView({ rootMargin })` is **added** to the nearest root's effective rect for that target
      only (it does not override provider margins).
- **Computation:** intersection rect, area ratio, threshold crossing per target; only crossings are dispatched.
  Dispatch is batched (`unstable_batchedUpdates`) so a scroll frame causes one React commit.
- **Scale:** targets of a root are re-measured each pass (correctness over caching), but a pass is skipped for roots
  whose own rect and scroll offset did not change and whose targets reported no layout. Builder may add spatial
  bucketing if the benchmark in §7 fails.
- **Fabric/old arch:** refs are host components; `collapsable={false}` is set on wrappers the library renders. For
  user-provided refs on flattened views, measurement returns zero size → treated as not visible, warn once in dev.

### 5.2 Later engines (design constraints only)

- **NativeIOEngine (v2.1):** when `typeof globalThis.IntersectionObserver === 'function'`, map the nearest root's host
  node to IO `root`, `rootMargin` to px string, thresholds directly; delay/AppState logic stays in shared JS.
- **ReanimatedEngine (v2.2):** `useAnimatedScrollHandler` + `measure()` in a shared worklet iterating registered
  targets; crossings sent to JS via `scheduleOnRN`. Fixes native-driver scroll. Reanimated stays an optional peer
  of the subpath only.

## 7. Testing and acceptance

- **Unit:** geometry (intersection, ratio, margins, nested clipping), threshold crossing state machine, dwell timers,
  scheduler coalescing (fake timers + mocked rAF).
- **Component:** `useInView`/`InView`/v1 wrappers with mocked `getBoundingClientRect` and `measureInWindow` paths;
  composition of user `onScroll`; AppState pause; `skip`; `triggerOnce`.
- **Device QA (manual, scripted with the example app):** Android emulator + iOS simulator, Expo Go latest: vertical
  list, nested horizontal carousel, header-clipped items, `triggerOnce`, `delay`, backgrounding the app, v1 example.
  Verify `getBoundingClientRect` accuracy during active scroll on Android (open risk).
- **Async fallback path (RN < 0.82):** covered by Jest, plus the example app exposes a dev toggle that forces the
  `measureInWindow` path on current devices; both platforms are QA'd with the toggle on. A bare app on the oldest
  supported RN version is best-effort, **not** a release gate. *(Author's call.)*
- **Benchmark:** 1,000 targets in a ScrollView on the Android emulator: idle JS thread work ≈ 0; continuous scroll keeps
  JS frame time < 8 ms on average; no React commits for targets that did not cross a threshold. Record results in the
  PR.
- CI: typecheck, unit/component tests, build, `npm pack` contents check.

## 10. Decisions made by the author (review these)

- Same package name, major bump (keeps downloads/SEO).
- Web-compatible API names (`useInView`, `InView`, `triggerOnce`, `skip`, `delay`) over v1-style names.
- Area-based `intersectionRatio` (web semantics); per-axis thresholds survive only in the v1 wrapper.
- Expo Go is the primary QA target.
- Provider required for scroll tracking; no-provider targets are static-screen only, with a dev warning (§4.1).
- `rootMargin` belongs to the root that declares it, applies after window clipping on the outermost root, carries
  into nested roots; target-level margins add on top (§5.1).
- Old-RN bare app QA is best-effort; the async path is covered by Jest and a forced-fallback toggle (§7).

Owner decisions (2026-11-04): v1 exports keep polling (§4.4); minimum React 18 / RN 0.72 (§3).
- AppState pause on by default.
- No caching of target positions in v2.0 (simpler, correct with dynamic layouts); optimise only if the benchmark fails.

## 12. Risks

- `getBoundingClientRect` freshness during scroll — **measured 2026-11-04** (300 `onScroll` samples, Expo Go,
  RN 0.88, comparing the sync read against `scrollViewY + childLayoutY − contentOffset.y`):
  - iOS 18.1 simulator: 0.0 % of samples off by > 1 pt (max 0.0, mean 0.00).
  - Android 15 emulator: 8.3 % off by > 1 pt (max 22.5 pt, mean 0.84) — the read can trail the scroll event by about
    a frame.
  - Decision (rule: > 10 % ⇒ async): both platforms default to `'auto'` (sync). The engine's trailing pass after
    scroll end settles any one-frame lag; revisit if users report threshold flicker on Android.
- `cloneElement`-based handler injection can be defeated by components that do not forward scroll props; mitigated by
  `useViewportRoot`.
- Native-driver scroll gets degraded behaviour until v2.2.
